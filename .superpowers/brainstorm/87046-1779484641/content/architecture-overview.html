Architecture Overview: Tessera-Based Evidence Ingestion

Tamper-evident log with witness verification

┌─── Evidence Submission ───┐
CI/CD Pipeline or K8s Service
↓ JWT token (OIDC)
↓
Gateway: POST /api/ingest
1. Verify JWT signature (JWKS discovery)
2. Extract (issuer, sub) from claims
3. Append to Tessera log → {log_index}
4. Publish to NATS: {log_index, yaml, publisher_identity}
5. Return 202 Accepted {log_index, job_id}
┌─── Async Processing ───┐
IngestWorker (NATS subscriber)
1. Receive: {log_index, yaml}
2. Parse YAML (Gemara)
3. Flatten to evidence rows
4. INSERT to PostgreSQL
   - Add log_index column
   - Store publisher identity
5. Publish evidence event
Certifier Pipeline
1. Schema validation
2. Provenance check
3. Executor verification
4. Publisher identity check
5. Write certification result
┌─── Witness Verification ───┐
Witness Service (internal)
1. Poll Tessera for new checkpoints
2. For each entry in checkpoint:
   a. Verify append-only (Tessera SDK)
   b. Check certification result (PostgreSQL)
   c. Verify publisher identity matches config
3. If all entries pass → countersign checkpoint
4. Publish countersignature to Tessera
Key Properties:
✓ Source of Truth: Tessera log (append-only, tamper-evident)
✓ Query Layer: PostgreSQL (rebuilt from Tessera if lost)
✓ Trust Signal: Witness countersignatures on checkpoints
✓ Audit Trail: Every evidence submission has immutable log_index

Storage Backends

  • Tessera: POSIX driver on Kubernetes PersistentVolume (cloud-agnostic)
  • PostgreSQL: Evidence, certifications, users, policies (query layer)
  • NATS: Event bus for async processing (existing infrastructure)

New Components

  • Tessera Appender: Library integrated into gateway process
  • Witness Service: New Go service, runs as K8s Deployment
  • JWT Verifier: OIDC token validation (adapted from current branch)

PostgreSQL Sync: Tessera Events vs NATS

Both are async, different integration points

B

Tessera Integration Events

POST /api/ingest
↓ tessera.Add(yaml)
↓ returns {log_index, future}
↓ 202 Accepted {log_index}
Background:
Tessera integration → entry readable
↓ Poll/callback mechanism
↓ Read entry from Tessera by index
↓ Parse YAML → Flatten → PostgreSQL
↓ Trigger certification pipeline

Pros

  • Simpler: one less component (no NATS)
  • Tessera is single source of truth
  • Can rebuild PostgreSQL from Tessera anytime
  • Direct dependency chain

Cons

  • Tessera has no built-in event notifications
  • Must implement polling or callback mechanism
  • Tighter coupling to Tessera integration timing
  • No built-in retry/backpressure/DLQ
  • Need to build queue semantics yourself
C

NATS Queue (Current Pipeline)

POST /api/ingest
↓ tessera.Add(yaml)
↓ returns {log_index}
↓ NATS publish: {log_index, yaml, publisher_id}
↓ 202 Accepted {log_index, job_id}
Background:
IngestWorker ← NATS subscribe
↓ Parse YAML → Flatten → PostgreSQL
↓ Store log_index with evidence
↓ Trigger certification pipeline
Recovery:
PostgreSQL lost → Read Tessera log from 0
↓ Republish to NATS → Rebuild DB

Pros

  • Reuses existing NATS infrastructure
  • Reuses existing IngestWorker logic
  • NATS provides retry, backpressure, DLQ
  • Decouples Tessera from PostgreSQL sync
  • Existing certification pipeline unchanged
  • Job tracking already built (IngestTracker)

Cons

  • One more component to operate (NATS)
  • Evidence YAML briefly duplicated (Tessera + NATS)
  • Slightly more complex architecture
Key Insight: NATS is already required for your certification pipeline (CertificationHandler subscribes to evidence events). Option C keeps that infrastructure and adds Tessera on top. Option B would need to replace NATS with custom polling/notification, which is harder to operate.
